Saya ingin melakukan perubahan arsitektur besar namun terkontrol pada aplikasi APKOSIS.

PENTING:
Jangan langsung mengubah kode sebelum memahami struktur aplikasi yang sekarang.
Pertama lakukan audit terhadap authentication, authorization, role, database, Supabase RLS, middleware, routing, query data, dan seluruh fitur yang sudah ada.

Tujuan utama perubahan ini adalah membuat APKOSIS menjadi aplikasi yang dapat digunakan lintas periode/kepengurusan dan diwariskan kepada adik kelas pada periode berikutnya, tanpa kehilangan data periode sebelumnya.

==================================================
1. KONSEP UTAMA APKOSIS
==================================================

APKOSIS akan digunakan terus-menerus untuk banyak periode kepengurusan.

Contoh:

Periode 2026/2027
Periode 2027/2028
Periode 2028/2029
Periode 2029/2030
dst.

Data dari setiap periode WAJIB tetap tersimpan dan tidak boleh tercampur.

Contoh:

Data keuangan periode 2026/2027
tidak boleh muncul sebagai data periode 2028/2029.

Data kendala periode 2026/2027
tidak boleh muncul sebagai data periode 2028/2029.

Data laporan divisi periode 2026/2027
tidak boleh muncul sebagai laporan periode 2028/2029.

Semua data harus memiliki hubungan yang jelas dengan periode.

Jangan hanya membuat filter tahun di frontend.
PERIODE HARUS MENJADI BAGIAN DARI DATA DAN QUERY DATABASE.

==================================================
2. HIERARKI ROLE BARU
==================================================

Buat arsitektur role sebagai berikut:

1. SUPER ADMIN
2. ADMIN
3. DIVISION ADMIN / KETUA-WAKIL DIVISI
4. MONITORING
5. BENDAHARA
6. SEKRETARIS

Jangan menghilangkan role yang sudah ada.

Jangan mengubah konsep dan fungsi utama:
- Monitoring
- Bendahara
- Sekretaris
- Ketua/Wakil Divisi

Perubahan utama adalah menambahkan struktur Super Admin dan Admin serta sistem periode yang benar.

==================================================
3. SUPER ADMIN
==================================================

SUPER ADMIN adalah pemilik/pembuat sistem APKOSIS.

Super Admin adalah saya sebagai pembuat aplikasi.

Super Admin memiliki akses tertinggi.

Super Admin BUKAN sekadar email yang dicek menggunakan hardcode di frontend.

Role Super Admin harus benar-benar tersimpan dan diverifikasi melalui sistem authorization yang aman.

Super Admin dapat:

- melihat seluruh periode
- melihat seluruh data
- membuat periode
- mengaktifkan periode
- mengarsipkan periode
- mengubah periode
- mengelola seluruh divisi
- mengelola akun Admin
- membuat Admin baru
- mengganti Admin
- mengubah email Admin
- reset password Admin
- mengelola akun divisi
- mengubah email akun divisi
- mengatur/reset password divisi
- mengaktifkan/nonaktifkan divisi
- melihat seluruh laporan
- melihat seluruh data keuangan
- melihat seluruh data kendala
- melihat seluruh data kebutuhan
- melihat seluruh data inventaris
- melihat seluruh periode lama
- memperbaiki data periode lama bila benar-benar diperlukan
- melakukan recovery jika terjadi masalah pada periode atau akun
- mengelola konfigurasi sistem yang bersifat global

Super Admin memiliki hak tertinggi terhadap data.

Namun jangan membuat Super Admin dapat melakukan sesuatu hanya karena tombolnya ditampilkan.

Authorization harus tetap diamankan di server/database/Supabase RLS.

==================================================
4. ADMIN
==================================================

ADMIN adalah pengelola APKOSIS untuk kepengurusan/periode yang sedang berjalan.

Contoh:

Periode 2026/2027
Admin = pengurus periode tersebut

Kemudian ketika aplikasi diwariskan:

Periode 2027/2028
Admin = adik kelas/pengurus baru

Super Admin tetap ada sebagai pemilik sistem.

Admin baru TIDAK menggantikan Super Admin.

Admin dapat mengelola kebutuhan operasional periode aktif sesuai permission yang diberikan.

Admin dapat:
- mengelola periode aktif sesuai kewenangannya
- mengelola konfigurasi divisi
- mengatur nama divisi
- mengatur nomor divisi
- mengaktifkan/nonaktifkan divisi
- mengelola akun divisi
- mengatur password divisi
- reset password divisi
- mengatur email akun divisi jika sistem memang menggunakan email tersebut
- melihat laporan periode aktif
- mengelola konfigurasi yang berkaitan dengan kepengurusan periode aktif

Namun:

ADMIN TIDAK BOLEH:
- menghapus Super Admin
- mengubah role Super Admin
- mengambil alih Super Admin
- mengubah kredensial Super Admin
- menghapus arsip periode lama
- sembarangan mengubah data periode lama
- mengakses fungsi khusus Super Admin

Jika diperlukan perubahan pada data lama, hanya Super Admin yang memiliki akses penuh untuk itu.

==================================================
5. ROLE DIVISI / KETUA-WAKIL
==================================================

Ketua/Wakil Divisi tetap menggunakan sistem APKOSIS seperti sekarang.

Mereka dapat:
- memilih/mengakses divisinya
- membuat laporan
- mengisi kegiatan
- mengisi kendala dan solusi
- mengisi inventaris
- mengisi kebutuhan
- mengisi pemasukan/pengeluaran jika fitur tersebut memang tersedia untuk divisi
- melihat status pengajuan
- melihat informasi divisinya sesuai permission

TETAPI:

HAPUS akses:
- pengaturan password divisi
- perubahan password divisi oleh Ketua/Wakil
- perubahan email akun oleh Ketua/Wakil
- perubahan konfigurasi divisi oleh Ketua/Wakil
- perubahan periode
- perubahan role
- pengelolaan akun

Password/email/konfigurasi divisi harus dikontrol oleh Admin atau Super Admin sesuai hak akses.

Jangan lagi memberikan tombol:

"Pengaturan password divisi"

di halaman role divisi.

Jika password perlu diganti, Ketua/Wakil harus meminta Admin.

==================================================

JANGAN mengubah konsep utama role Monitoring.

Monitoring tetap dapat:
- melihat data
- melakukan monitoring
- melihat laporan
- melihat keuangan
- melihat kendala
- melihat informasi seluruh divisi sesuai permission

Namun Monitoring harus bisa memilih PERIODE.

Contoh:

SEMUA DATA PADA HALAMAN TERSEBUT HARUS BERASAL DARI PERIODE 2028/2029.

Bukan hanya label dropdown yang berubah.

==================================================
7. BENDAHARA
==================================================

JANGAN mengubah konsep utama role Bendahara.

Bendahara tetap memiliki fitur keuangan yang sekarang.

Namun seluruh data keuangan harus terikat ke periode.

Contoh:

Periode 2028/2029
- pemasukan
- pengeluaran
- pengajuan dana
- status dana
- penggunaan dana
- rekap keuangan
- detail transaksi

Jika Bendahara memilih:

2026/2027

maka seluruh data keuangan yang ditampilkan harus berasal dari periode 2026/2027.

Data periode lama bersifat READ-ONLY untuk Bendahara.

Bendahara tidak boleh mengedit atau menghapus transaksi periode lama.

==================================================

Jangan pernah mencampurkan beberapa periode kecuali memang ada fitur khusus "Semua Periode" yang hanya dapat digunakan oleh Super Admin jika diperlukan.

==================================================
13. DROPDOWN PERIODE HARUS BENAR-BENAR MEMFILTER DATABASE
==================================================

JANGAN melakukan:

Dropdown berubah menjadi 2026/2027
tetapi query masih mengambil semua data.

Contoh yang SALAH:

SELECT *
FROM transactions;

lalu frontend hanya mengganti tulisan tahun.

Itu TIDAK BOLEH.

Harus benar-benar menggunakan:

periode_id

dalam query/database filtering.

Contoh konsep:

SELECT *
FROM transactions
WHERE periode_id = selected_periode_id;

Sesuaikan implementasi dengan Supabase dan arsitektur aplikasi saat ini.

==================================================
17. PERIODE AKTIF VS PERIODE ARSIP
==================================================

Periode aktif:

- dapat digunakan untuk input data
- role yang memiliki permission dapat membuat data
- laporan baru dapat dibuat
- transaksi baru dapat dibuat
- pengajuan baru dapat dibuat

Periode archived:

- dapat dilihat
- dapat dicari
- dapat difilter
- dapat direkap
- dapat diexport sesuai permission
- TIDAK dapat diedit oleh role biasa
- TIDAK dapat dihapus oleh role biasa

Super Admin memiliki kemampuan khusus untuk memperbaiki data arsip jika diperlukan.

==================================================
18. JANGAN HANYA MENAMBAHKAN READ-ONLY DI FRONTEND
==================================================

Jangan hanya melakukan:

if (periodArchived) {
  disableButton()
}

Itu tidak cukup.

Pastikan database/RLS/server authorization juga mencegah:

INSERT
UPDATE
DELETE

pada periode archived untuk role yang tidak memiliki izin.

User tidak boleh bisa melewati UI dengan memanggil endpoint/query secara langsung.

==================================================
19. DATA LAMA HARUS AMAN
==================================================

Sebelum migrasi database:

- lakukan audit
- buat migration yang aman
- jangan menghapus data existing
- jangan melakukan destructive migration tanpa alasan
- jangan mengganti struktur secara sembarangan

Data yang sekarang sudah ada harus tetap tersedia.

Jika tabel existing belum memiliki periode_id:

buat strategi migrasi.

Contoh:

Semua data existing yang memang merupakan data periode 2026/2027 diberi:

periode_id = periode 2026/2027

Jangan sampai data lama menjadi NULL tanpa alasan.

Jika ada data yang periode asalnya tidak dapat diketahui dengan pasti, JANGAN menebak.
Tandai dan laporkan kepada saya file/tabel/data yang membutuhkan keputusan manual.

==================================================
20. DIVISI DAN PERIODE
==================================================

Perlu dibedakan antara:

DIVISI
dan
KEANGGOTAAN DIVISI PADA PERIODE TERTENTU.

Contoh:

Divisi 01 = Keamanan

Divisi tersebut dapat tetap ada di banyak periode:

2026/2027 → Divisi 01 Keamanan
2027/2028 → Divisi 01 Keamanan
2028/2029 → Divisi 01 Keamanan

Namun konfigurasi, akun, dan data yang berkaitan dengan kepengurusan harus dapat dikaitkan dengan periode yang benar.

Jangan sampai data Divisi 01 periode 2026 otomatis bercampur dengan Divisi 01 periode 2028.

Jika nama divisi dapat berubah antarperiode, desain database harus tetap mampu menangani perubahan tersebut.

==================================================
21. AKUN DIVISI
==================================================

Konsep akun divisi yang sekarang sudah ada harus dipertahankan sejauh memungkinkan.

Namun kredensial divisi dikontrol oleh:

SUPER ADMIN

ADMIN sesuai permission.

Ketua/Wakil tidak dapat mengganti password sendiri.

- membuat/mengatur akun divisi
- reset password
- mengatur hubungan akun dengan divisi/periode

Super Admin dapat mengontrol semuanya.

Jangan menyimpan password plaintext.

Jangan mengekspos service_role key di browser.

==================================================
5A. HUBUNGAN SUPER ADMIN DAN ADMIN ANTAR PERIODE
==================================================

APKOSIS dirancang sebagai sistem jangka panjang yang akan diwariskan dari satu generasi pengurus OSIS ke generasi berikutnya.

SUPER ADMIN adalah pemilik/pengelola tertinggi sistem APKOSIS dan tetap berada di atas seluruh periode.

ADMIN adalah pengelola operasional untuk periode kepengurusan tertentu dan dapat berganti setiap kali periode berganti.

CONTOH:

Periode 2026/2027
→ Admin: Sofwatunida

Periode 2027/2028
→ Admin: Adik Kelas A

Periode 2028/2029
→ Admin: Adik Kelas B

SUPER ADMIN tetap sama dan tidak ikut berganti hanya karena periode berganti.

==================================================
5B. PERAN SUPER ADMIN DALAM PERGANTIAN GENERASI
==================================================

Super Admin tidak perlu mengurus operasional harian setiap periode.

Tugas Super Admin adalah menjaga dan mengontrol sistem secara keseluruhan.

Super Admin dapat:

1. Membuat periode baru.
2. Menentukan periode aktif.
3. Menentukan siapa Admin untuk periode tersebut.
4. Mengubah atau mengganti Admin.
5. Menonaktifkan Admin.
6. Melakukan reset/recovery akun Admin.
7. Mengelola seluruh akun divisi.
8. Mengelola seluruh konfigurasi sistem.
9. Melihat seluruh data seluruh periode.
10. Mengakses arsip seluruh periode.
11. Melakukan koreksi data arsip jika benar-benar diperlukan.
12. Melakukan recovery apabila terjadi masalah.
13. Mengontrol struktur role dan permission.

Super Admin TIDAK harus ikut melakukan pekerjaan operasional Admin setiap hari.

Setelah periode baru diserahkan kepada Admin baru, Admin baru bertanggung jawab atas operasional periode tersebut.

==================================================
5C. ADMIN BERDASARKAN PERIODE
==================================================

Admin harus memiliki hubungan yang jelas dengan periode yang menjadi tanggung jawabnya.

Contoh:

Admin A
→ bertanggung jawab terhadap periode 2027/2028.

Admin B
→ bertanggung jawab terhadap periode 2028/2029.

Admin tidak otomatis memiliki kontrol penuh terhadap seluruh periode hanya karena memiliki role "admin".

Authorization harus mempertimbangkan:

- role
- periode
- permission

Jangan hanya melakukan:

role = admin → boleh mengakses semua data.

Sebaliknya:

ADMIN
→ boleh mengelola operasional periode yang ditugaskan kepadanya.

SUPER ADMIN
→ boleh mengakses seluruh periode.

==================================================
5D. PROSES PERGANTIAN ADMIN
==================================================

Ketika periode baru akan dimulai, prosesnya:

1. Super Admin membuat periode baru.

Contoh:
2027/2028

2. Super Admin menentukan Admin periode tersebut.

Contoh:
Admin = Adik Kelas A

3. Sistem menghubungkan Admin tersebut dengan periode 2027/2028.

4. Super Admin mengaktifkan periode 2027/2028 ketika periode tersebut mulai digunakan.

5. Periode sebelumnya:
2026/2027

diubah menjadi:

ARCHIVED

6. Data 2026/2027 tetap tersimpan.

7. Admin baru mulai mengelola periode 2027/2028.

8. Admin baru TIDAK memperoleh hak Super Admin.

==================================================
5E. ADMIN TIDAK BOLEH MENGAMBIL ALIH SUPER ADMIN
==================================================

Admin tidak boleh memiliki kemampuan untuk:

- mengubah role dirinya menjadi super_admin
- membuat dirinya sendiri menjadi Super Admin
- mengubah akun Super Admin
- mengganti email Super Admin
- mengganti password Super Admin
- menghapus Super Admin
- menonaktifkan Super Admin
- menghapus role super_admin
- memberikan role super_admin kepada user lain

Semua tindakan tersebut hanya boleh dilakukan melalui mekanisme khusus Super Admin jika memang diperlukan.

Jangan membuat endpoint yang memungkinkan Admin melakukan privilege escalation.

==================================================
5F. ADMIN TIDAK BOLEH OTOMATIS MENGUASAI PERIODE LAMA
==================================================

Ketika Admin baru ditetapkan untuk periode baru:

Contoh:

Admin B
→ periode 2028/2029

Admin B tidak otomatis mendapatkan hak edit terhadap:

2026/2027
2027/2028

Data periode lama tetap dapat dilihat jika permission mengizinkannya, tetapi bersifat READ-ONLY.

Contoh:

Admin B dapat:

VIEW 2026/2027 → sesuai permission
VIEW 2027/2028 → sesuai permission
EDIT 2026/2027 → ❌
EDIT 2027/2028 → ❌
DELETE 2026/2027 → ❌
DELETE 2027/2028 → ❌

Super Admin tetap memiliki akses khusus terhadap arsip.

==================================================
5I. SUPER ADMIN TETAP MENJADI PEMILIK SISTEM
==================================================

Walaupun Admin dapat berganti setiap periode, Super Admin tetap menjadi pemilik/pengelola tertinggi aplikasi.

Konsep akhirnya:

SUPER ADMIN
= pengontrol dan penjaga sistem APKOSIS lintas generasi.

ADMIN
= pengelola operasional APKOSIS pada periode tertentu.

ROLE OPERASIONAL
= pengguna fitur sesuai fungsi masing-masing.

Dengan demikian, ketika saya lulus dan APKOSIS diserahkan kepada adik kelas:

Saya tidak perlu ikut mengelola laporan harian, keuangan, kendala, atau administrasi periode baru.

Adik kelas cukup menerima akun ADMIN untuk periode mereka.

Saya tetap memiliki akun SUPER ADMIN untuk:

- recovery
- pengawasan sistem
- pemeliharaan
- pengaturan periode
- penggantian Admin
- perlindungan arsip
- pengelolaan konfigurasi tingkat tinggi

Tujuan akhirnya adalah APKOSIS dapat digunakan selama bertahun-tahun tanpa harus membuat ulang aplikasi atau database setiap pergantian kepengurusan.
